La solución

Un proxy FinOps entre tus equipos y los proveedores de IA

Habla la API de OpenAI en ambas direcciones: los clientes no cambian nada, y cada proveedor se conecta con el mismo estándar. Cada petición queda clasificada, enrutada, presupuestada y auditada.

Cómo funciona

Cada petición pasa por un pipeline de decisión

01

Auth

Keys internas finops_key_* con scope aislado. Las claves de proveedor nunca salen del proxy.

02

Clasificación

Categoría + complejidad + capabilities. Reglas deterministas; LLM barato solo si hay duda.

03

Routing

El modelo más barato capaz de hacer el trabajo, entre 3 proveedores.

04

Presupuesto

Política por consumidor: warn → degradar 1 tier → bloquear 429.

05

Caché semántica

pgvector, similitud coseno ≥ 0,95 → respuesta a coste $0.

06

Auditoría

Tokens reales, coste por tarifa de catálogo, alertas y forecast en cada fila.

El cliente envía model = auto y el proxy responde con formato OpenAI estándar. Todo lo demás — decisión, coste, ahorro — queda registrado y es verificable.

Arquitectura y diferenciación

Diseñado como lo querría un CTO en producción

Un estándar en ambas direcciones

API OpenAI al recibir y al llamar upstream. OpenWebUI y opencode funcionan apuntando a localhost:8000/v1 — cero cambios de código.

Multi-proveedor por YAML

OpenRouter, Fireworks y TabbyAPI local hablan el mismo estándar: añadir un proveedor es configuración, no código.

Inferencia local SOTA

TabbyAPI con ExLlamaV3 (cuantización EXL3): mejor throughput/VRAM que Ollama, misma API.

Caché semántica $0 / hit

pgvector + similitud coseno ≥ 0,95: prompts equivalentes se sirven de caché al instante.

Seguridad de claves

Las claves de proveedor viven solo en el proxy, inyectadas server-side. Scope por consumidor: 403 entre equipos.

Informes CSV / PDF

Exportes de coste descargables con filtros por consumidor y fechas. Listos para finanzas.
